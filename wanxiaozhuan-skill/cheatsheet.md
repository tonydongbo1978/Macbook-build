# 速查表：写 Skill 的决策规则

## 决策规则（当 X，做 Y，因为 Z）

| 当… | 做… | 因为… |
|---|---|---|
| 任务是重复、专业、要求稳定 | 做成 Skill | 提示词给不了一致输出（ch01） |
| 任务是一次性、探索性 | 别做 Skill，用提示词 | 维护成本大于收益（ch01） |
| 一个 Skill 想管多件事 | 拆成多个单一职责 Skill | 分支越多模型越困惑（ch06） |
| 不确定该不该上脚本 | 先问"10 个人做结果一样吗" | 一样→脚本；各有千秋→策略；格式同→模板（ch08） |
| 环节必须精确（金额/格式/换算） | 交给脚本 | 模型会算错、会漂移（ch08） |
| 环节需要判断（审稿/选品/诊断） | 用策略指引 | 灵活发挥是优势（ch08） |
| 输出格式必须统一 | 用模板框架 | 结构固定、内容可填（ch08） |
| 要写 SKILL.md 正文 | 只写指令，不写解释 | 解释是噪声（ch06） |
| 步骤写不清 | 用"动词+顺序"重写，并做新员工测试 | 读不懂的指令模型也执行不了（ch06） |
| 只想到正常流程 | 补失败处理（打不开/太短/不是这个/缺信息） | 否则模型会瞎编或死循环（ch06） |
| 写完不知好不好 | 先写评估用例再改 | 没有考题就没有改进方向（ch06） |
| 要处理 200 份文件 | 脚本/子智能体预处理 | 上下文必爆（ch06） |
| 知识库一堆 PDF | 先批量转纯文本 | 每次解析都慢且贵（ch07） |
| 文件名是"规则.md" | 改成自解释的长名 | 文件名是最便宜的索引（ch07） |
| Skill 越来越多 | 建索引 + 权威来源 + Owner | 否则找不到、改坏、版本混乱（ch12） |
| 要分享 Skill 给外部 | 先做安全审查、去密钥 | 分享=交出部分执行权限（ch03） |

## 阈值与数字（书中锚点）

- **正文长度**：SKILL.md ≤500 行、≤5000 tokens（中文约 7500–10000 字）；超出拆 references（ch02）。
- **元数据**：只有 name/description 必填；name 不能中文（ch02）。
- **上下文**：同时加载几十个 Skill 的元数据，占用"微乎其微"（ch02）。
- **模型差距**：10 步任务，强模型成功率 >90%，弱模型可能 <30%（ch03）。
- **知识粒度**：回答一个典型问题常需 >5 个文件 → 太细；只用一小部分 → 太粗（ch07）。
- **管理规模**：1 人～3 人做 3 件事；十几人以上加 4 件事（ch12）。
- **复用账**：2 小时写一个 Skill，可能省 200 小时重复劳动（ch01）。

## 识别信号（看到这些，说明 Skill 写坏了）

- description 是"这是一个很实用的工具" → 永远不会被正确触发（ch06）。
- 正文在解释"本 Skill 旨在…" → 写成了给人看的文档（ch06）。
- 步骤里出现"分析内容、给出专业建议" → 空话，模型无法执行（ch06）。
- 没有失败处理 → 遇到脏输入就崩（ch06）。
- 所有环节都写脚本 → 维护地狱、安全面扩大（ch08）。
- references 里全是 PDF/Word → 每次执行都在重复解析（ch07）。
- 同一个 Skill 在不同机器上路径失效 → 用了绝对路径或 `../`（ch02）。

## 一句话判据

> **Skill 的质量 = 触发准（description）× 执行稳（流程+失败处理）× 越用越省（上下文与知识库）。**
