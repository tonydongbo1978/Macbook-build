# 第 6 章：Skill 设计的核心法则

## 核心思想
"会创建"和"创建得好"是两件事。好 Skill 的三个前提是**把它当能力模块而非提示词、写给模型看而非给人看、单一职责而非大而全**；五条标准是**元数据准、边界清、输入输出明、步骤可执行、失败处理全**；而质量提升靠**工作流 + 检查清单 + 闭环反馈 + 评估驱动**。

## 本章框架

- **写之前必须知道的 3 件事**：
  1. **Skill 不是提示词**：提示词可模糊、求灵活；Skill 必须精确、求确定性（同一输入→同一质量输出）。
  2. **Skill 是写给模型看的**：不要解释"本 Skill 旨在…"，只写"当…时，按以下步骤…"。每一行都是指令，不是背景。
  3. **不是越复杂越强大**：分支越多，模型越困惑；上下文是共享资源，长 Skill 会挤压其他 Skill。**单一职责**——一个 Skill 只做一件事。
- **五大核心设计标准**（以"合同风险扫描"为例）：
  1. **元数据要准确**：name 小写连字符；description 用第三人称，说清"输入是什么、输出是什么、何时触发"。
     - 差："这是一个很实用的合同审核工具。" 好："浏览合同文本，识别对用户不利的风险条款并给出修改建议。当用户提供合同文件并询问合同存在的问题时触发。"
  2. **边界要清晰**：正向条件（何时用）+ 易混时补负向条件（如"用户要求起草新合同时不要用本 Skill"）。
  3. **输入输出要明确**：输入（必需/可选，如合同文本、用户身份、关注重点）；输出（风险等级、条款清单、修改建议、谈判要点）。
  4. **步骤要可执行**：动词开头、顺序明确（确认→通读→提取→逐条检查→标注→给替代条款）；但**不要穷举**，给框架和典型示例，让模型举一反三。
     - 检验法：读给一个新员工听，他能照做，模型也能。
  5. **失败处理要完整**：文件打不开、文本过短、内容不是合同、用户没说明立场——每种都给一句标准应对，否则模型会瞎编或死循环。
- **让执行可控的三件套**：
  - **工作流**：明确阶段与顺序；
  - **检查清单**：执行中逐项打钩（已确认竞品≥3、已收集基础信息、已完成对比表、已提炼差异点、已给行动建议）；
  - **闭环反馈**：关键节点"验证→修正→继续"（信息是否完整、是否最新、来源是否可靠）；
  - **交付前自检**：把输出要求逐条复述让模型自查（字数、卖点数、语气、CTA、禁提竞品），不达标先改再交。
- **评估驱动、失败优先（最有价值的方法论）**：
  1. **先让智能体裸跑**（不带 Skill 做一遍），观察失败；
  2. **失败点即需求清单**（卖点太泛、没对比、重复、不对用户痛点）；
  3. **先写考题再写答案**：评估用例＝输入场景 + 期望标准（含"连跑 3 次结果一致"这类稳定性要求）；考题**不写进 Skill**（否则等于泄题）；
  4. **最小 Skill + 持续迭代**：先解决核心问题，每次加规则后**回归所有用例**，防"按下葫芦浮起瓢"。
- **Skill 之间的互相调用**：复杂任务拆成多个单一职责 Skill；三原则＝**输入输出标准化**、**保持独立性**（不强制依赖）、**在 SKILL.md 中声明协作方式**。
- **省上下文的三个技巧**（核心一句：能在上下文外干的活，不要搬进来）：
  1. **脚本替代读文件**：10 万行表格→脚本算完只输出"总额 320 万、同比 12%、退货率 3.2%"；
  2. **脚本内调用另一个大模型（API）**：批量摘要/提取，中间过程不进主上下文，可选用便宜模型预处理；
  3. **子智能体**：独立上下文，只回传最终结果（适合可独立完成的子任务）。

## 关键概念
- **单一职责**：一个 Skill 一个核心动作。
- **评估用例**：输入+期望标准组成的"考题"。
- **回归测试**：每次改规则后重跑全部用例。
- **闭环反馈**：验证→修正→继续。
- **上下文外处理**：脚本/子智能体承接重活。

## 心智模型
- **"Skill 是军令，不是散文"**：可执行、无歧义。
- **"先看它怎么失败，再决定写什么"**：失败优先，避免凭空设计。
- **"考题先于答案"**：没有验收标准的 Skill，改到最后也不知道好不好。

## 反模式
- 一个 Skill 管周报、纪要、邮件、公告（应拆四个）。
- 用"分析合同内容、给出专业建议"这类空话当步骤。
- 穷举几十种风险类型（限制模型判断力）。
- 考题写进 Skill（模型提前知道答案，测不出真实水平）。

## 关键结论
1. 五条标准是可逐项打钩的验收表，写完必查。
2. 检查清单 + 交付前自检，能消掉大部分"漏要求"的问题。
3. 评估驱动是唯一能让 Skill"越改越好"而不是"越改越乱"的方法。
